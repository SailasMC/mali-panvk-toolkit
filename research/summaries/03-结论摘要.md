# 03 号研究结论摘要（libgralloctypes 能力边界）

## 一句话
**纯 NDK 无法绕开 gralloc**；能拿到的只有"线性缓冲"所需的信息，**拿不到 drmFormatModifier** —— 而 panvk 恰恰要它。

## 1. libgralloctypes 的 API 性质
- 公开 23 个 `MetadataType_*` 常量 + 各自 encode/decode 对；Mesa 只用 5 个 decode：
  `decodePixelFormatFourCC(7)` / `decodePixelFormatModifier(8)` / `decodePlaneLayouts(15)` /
  `decodeDataspace(17)` / `decodeChromaSiting(14)`
- decode 系列**是纯函数**（只吃 `hidl_vec<uint8_t>` + 常量），**但字节流唯一来源是
  IMapper@4.0 HIDL 的跨进程 get()** ⇒ libgralloctypes 里**没有** native_handle → fourcc/modifier 的本地路径
- mapper5 路线改用 header-only `android/hardware/graphics/mapper/utils/IMapperMetadataTypes.h`
  （`libgralloctypes` 在 mapper5 设备上**根本不被使用**）⇒ 两条路都指向 gralloc HAL 服务

## 2. NDK `AHardwareBuffer_describe` 能给/不能给
| 能推导 | 不能得到 |
|---|---|
| `fourcc` ← `desc.format`（`AHardwareBuffer_convertFromPixelFormat` 是**恒等函数**，即原始 HAL_PIXEL_FORMAT；但 `IMPLEMENTATION_DEFINED(0x22)` 无解） | **`drmFormatModifier`** —— NDK/VNDK/libui **全都没有该 API** ✗ |
| `rowPitch` ← `desc.stride × bpp` | 压缩格式的 metadata plane |
| `offset` ← `lockPlanes().data` 相减（需 CPU 可锁） | 多 dma-buf disjoint 判定、chroma siting |
| `fd` ← `AHardwareBuffer_getNativeHandle`（**仅 VNDK**，NDK 没有） | |

## 3. 为什么不能完全绕开
- **纯 NDK 连 dma-buf fd 都拿不到** ⇒ `VkImportMemoryFdInfoKHR` 无法构造 ⇒ 不可行
- **VNDK + 自算** 仅对"线性、无压缩、平面可枚举"的 buffer 成立，
  等价于 Mesa **现成的 `U_GRALLOC_TYPE_FALLBACK`**（modifier=DRM_FORMAT_MOD_INVALID、offset=0、rowPitch=stride×bpp）
- ⇒ **缺口核心就是 modifier**：panvk 会把它喂给 `panvk_image_get_explicit_mod()`
  （`panvk_image.c:307-331` 的 `assert(panvk_image_can_use_mod(...))`）—— **猜错则 assert 或静默读错像素**

## 4. 对路线的直接指导
1. **压缩（AFBC/AFBC-compressed）buffer ⇒ 必须走 IMapper**（4.0 HIDL 或 5.x AIDL）
2. **线性 buffer ⇒ 复用/实现一个"AHB 直读"后端即可**（无需 libgralloctypes）
3. **不要新写 libgralloctypes 解码器**（没有本地字节流来源）
4. ⇒ 因此**能否成功**取决于：**SurfaceFlinger/gralloc 给这个应用的交换链 buffer 是不是线性的** ✗值得实测
