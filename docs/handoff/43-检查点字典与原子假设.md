## 1. 读出方式（超时快照里的日志行）

```
kbase: CKPT timeout snapshot subqueue N word 0x<c0dexxxx> => id 0x<id> (<名字>)
若 word 不匹配 MAGIC ⇒ "no checkpoint of …" ⇒ 说明该子队列从没走到任何检查点
```
机制：`panvk_per_arch(kbase_checkpoint)()` 用**唯一常量 STORE**（非累加 ✗）写入该子队列
**seqno cell 的 offset 56** ✓（stride 64；0..51 已占：sync64 0..15 / LS copy 16..23 / wrapper marks 24..47 / progress 48..51 ✓）
⇒ **不会进位污染** ✓（这正是旧 progress 位图不可解读的根因 ✗）

## 4. 当前两个竞争假设（第三方模型 GLM 给的，必须切开 ✗）

| 假设 | 内容 | 与观测是否自洽 |
|---|---|---|
| **A（原子能力）** | SYNC_ADD64 这个**原子加**打到的内存**不支持原子**（属性/缓存策略不匹配）⇒ 原子 ack 永不到来 ⇒ CS 静默挂死 ✗ | 自洽 ✓（无 fault ✓ kick 无效 ✓ 计数冻住 ✓）|
| **B（可见性/一致性）** ⭐ | 该内存是 **CPU 侧缓存映射** ⇒ GPU 的原子写/检查点写**落在不 coherent 的域** ⇒ 原子**可能已落盘** ✓，而 CPU 与共享队列内存读到的**全是陈旧副本** ✗ | **同样自洽** ✓ 且与 A **共用全部现有观测** ✗ ⇒ **无法据此区分** ✗ |

### ⚠️ 被修正的旧读数（不要再当证据 ✗）
```
· "CS_STATUS_WAIT = 0 ⇒ 固件不在等待" ✗ —— 该数来自 v66 的【页2 诊断】，
  而页2【已被证明不镜像内核 CS 寄存器块】✗ ⇒ 该数据不可信 ✗（GLM 指出 ✓）⇒ 已从证据链剔除
· "无 fault" 只是【弱否定】✗（CS_FAULT 读不到 + 日志静默 ≠ 无故障）
· 凡是通过 CPU 映射读出的 seqno/extract/insert，都要先声明【读自哪种映射】✗ 否则可能是陈旧快照
```
